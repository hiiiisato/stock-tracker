# 株式分割・併合に対応する価格データの保持・更新設計案

作成日: 2026-11-03（JST）
位置付け: 2026-11-03時点の設計案。無料案＋12週経過後のJ-Quants照合を採用。実装・検証状況は [実装記録](price_adjustment_implementation_2026-11-07.md) を参照。
関連調査: [キオクシアの障害調査](kioxia_split_investigation_2026-11-03.md)

## 1. 推奨する流れ

公式情報から分割予定を登録 → 権利落ち日に適用対象化 → 価格の取得原本を保存 → 価格基準を統一 → 調整済みOHLCVを再生成 → 検証済みの版を公開 → 全画面・指標が共通の取得処理から参照。

元の記録を残し、分割台帳から何度でも同じ結果を再構築できることを基本にする。すでに補正された数値へ係数を繰り返し掛ける更新方式は採用しない。

公式イベントが存在するかどうかと、取得した価格へ追加調整が必要かどうかは別の状態として管理する。価格に段差が見えないことを理由に、確認済みの分割イベントを削除・不採用にしない。

## 2. 一般的な提供仕様で確認できること

[J-Quantsの公式株価仕様](https://jpx-jquants.com/ja/spec/eq-bars-daily)は、調整前のO/H/L/C/Vo、権利落ち日のAdjFactor、調整後のAdjO/AdjH/AdjL/AdjC/AdjVoを分けて提供している。調整前の値は分割等によって遡及変更せず、調整後の値を遡って再計算する。通常のデータ訂正があり得るため、取得原本と訂正履歴をアプリ側でも保持する。

[Alpha Vantageの公式仕様](https://www.alphavantage.co/documentation/#dailyadj)にも、当時のOHLCV、調整済み終値、分割・配当イベントを分けて返す例がある。ただし各社で調整対象は異なる。「adjusted」という名称だけで配当を含むかどうかを判断しない。

本案のデータ保持・公開方式は、これらの提供仕様を参考にしたアプリ側の設計提案であり、提供元内部のDB構造を断定するものではない。

## 3. 保持するデータ

| 種類 | 内容 | 更新のルール |
|---|---|---|
| 取得原本 | 提供元から受け取ったOHLCV、取得日時、要求範囲、応答のハッシュ、提供元の調整仕様 | 元の観測を保存。訂正・再取得は別の版として追跡し、同じ内容の重複保存は省く |
| 分割等の台帳 | 銘柄、種類、権利落ち日、基準日、効力発生日、旧株数・新株数、公式出典、発表・訂正・取消、情報の版 | 公式情報で更新。予定・確認済み・取消・情報不一致を区別する |
| 基準を統一した当時値 | その日に取引された基準のOHLCV、根拠となる観測・公式情報 | 出典が説明できる行だけ作る。既存のclose列を無条件で当時値と認定しない |
| 調整済み価格 | 始値・高値・安値・終値・出来高、累積係数、調整方針、基準日、生成版 | 当時値と台帳から再生成。公開中のデータへ直接掛け算して更新しない |
| 公開状態 | 銘柄別の公開中の版、価格日、台帳の版、検証結果、保留理由 | 検証済みの版へ一括切替。新旧の価格基準が途中で混ざらないようにする |

実装時の候補は、取得原本テーブル、既存stock_splitsの拡張、当時値テーブル、調整済み価格テーブル、銘柄別公開状態テーブル。詳細な物理設計は既存の行数・容量・クエリ負荷を確認して確定する。

既存列の互換性を保って追加し、移行中は旧・新の読取結果を比較する。既存データは移行完了まで保存し、出典不明の価格へ「確認済み」の既定値を付けない。

## 4. 係数と価格の定義

分割・併合について、旧株数をbefore、新株数をafterとすると、価格に掛ける係数はbefore/after、出来高に掛ける係数はafter/before。

調整基準日をB、価格日をdとし、dより後、B以前の権利落ち日に対応する係数を累積する。分割当日の新基準の価格へ、その日の分割係数をもう一度掛けない。将来予定のイベントは権利落ち日までは価格に反映しない。

キオクシアの例（2026-09-29以降を基準にする場合）:

| 日付 | 当時値の終値 | 価格係数 | 調整後終値 |
|---|---:|---:|---:|
| 9月25日 | 55,780 | 1/3 | 18,593.333… |
| 9月28日 | 53,340相当 | 1/3 | 17,780 |
| 9月29日 | 17,880 | 1 | 17,880 |

9月28日の53,340は調査で得たYahooの分割後基準17,780×3による換算値。移行時は公式データとの照合対象とし、計算例だけで公式の当時値として確定しない。

比率は3:1などの整数比と原文を保持し、1/3を最初に0.333333へ丸めて累積しない。始値・高値・安値・終値を同じ係数で調整し、計算途中の丸めを避ける。表示・提供元との照合では相手の丸め仕様を明示する。

[J-Quantsの計算仕様](https://jpx-jquants.com/ja/spec/eq-bars-daily/adj)は分割・併合に加えてライツイシューも扱い、現金配当は調整対象外。ライツイシューの出来高は価格係数の逆数では調整しない。台帳に種類と価格係数・株数係数を別々に持ち、特殊な権利処理へ単純な分割式を流用しない。

標準チャートは現金配当を含めない方針を維持し、配当込みリターンを追加する場合は別の系列・別の表示として扱う。

週足・月足は調整済み日足から集計する。先に未調整の週足・月足を作ると、期間途中の分割を正しく反映できない。

## 5. 分割予定の取得・確定

### 無料を維持する案

- [JPX「配当落・権利落等情報」](https://www.jpx.co.jp/listing/others/ex-rights/index.html)を毎営業日取得する。掲載範囲は公表日から2週間先まで、更新目安は13時、過去分は直近4営業日なので、取得した原本を蓄積する。
- 実際の[2026-11-02公表Excel](https://www.jpx.co.jp/listing/others/ex-rights/nlsgeu000004rws9-att/20261102.xls)を読み取り、基準日・実質上の基準日・権利落日（普通取引）・銘柄コード・備考・更新フラグがあることを確認した。**分割比率の列はない**。備考の「分割」は検知に使い、比率は会社のTDnet公式開示本文等から確定する。
- 会社開示は、対象銘柄・日付・分割比率・訂正・取消まで照合する。抽出が曖昧なものをAIの推定だけで確定しない。株式無償割当・投資口・併合等は種類に応じて取り扱いを定義する。
- JPX「権利処理に関する情報」は信用取引の調整対象として公表される情報であり、全銘柄を網羅する台帳とみなさない。補助照合に使う。
- 日次取得の長期停止は、会社開示と[JPX統計月報の新株落・権利落等一覧](https://www.jpx.co.jp/markets/statistics-equities/monthly/index.html)等で復旧する。月報未公表などで確定できない区間は保留する。
- Yahooのsplitsは取りこぼしを発見する補助候補にとどめ、公式台帳を上書きする権威にはしない。
- J-Quants Freeが取得できる範囲に入った日付を日々取り込み、公式の当時値・係数と照合する。Freeでは直近12週間の当時値を取得できない制約が残る。

価格の急変は調査対象を見つける検査として利用できるが、その急変だけで分割イベント・分割比率を生成しない。

### 当日から公式価格へそろえる案

[J-Quants Light](https://jpx-jquants.com/ja)は月額1,650円（税込）、日足の過去5年分、60回/分。株価・係数を同じ公式提供元にそろえ、Yahooの価格基準を復元する処理への依存を減らせる。

公式のAdjO/AdjH/AdjL/AdjC/AdjVoを取り込む場合は、台帳の係数をさらに掛けない。当時値・係数も保持し、再計算結果との整合を検証する。過去のAdj項目が後続の分割によって変わるため、当日分の追記だけでは更新が完了しない。分割・係数変更を検出した銘柄の必要な過去期間を再取得する。

株価更新の公式目安は[16:30頃](https://jpx-jquants.com/ja/spec/data-update)。現行の16:17開始便をそのまま流用せず、17時台の本便・後続便による補完と、要求日付の収録確認を組み合わせる。目安時刻だけで取得完了とはみなさない。

個人向け契約は本人利用が前提。[公式の利用条件](https://jpx-jquants.com/ja/help/usage)に合わせ、第三者がデータを閲覧できる公開範囲の見直しも導入条件に含める。無料プランにも同じ条件がある。一時契約後に無料へ戻して上位プランの生データを保持し続ける案は採用しない。

技術的には、安定性と保守負担を優先するならLightへの統一が有利。現行の無料方針を守る案も用意できるが、複数情報源の突合と不一致時の保留処理が必要になる。料金支払いで表示経路の不備やデータ公開途中の混在が自動的に直るわけではなく、保存・参照設計はどちらの案でも変更する。

## 6. Yahooを使用する場合の必須ルール

Yahooから受け取ったcloseを、無条件で当時の実際の終値として保存しない。

1. 取得原本を出典・取得時点付きで保存する。
2. 分割後基準に調整済みのレスポンスの場合、どの分割まで織り込まれているかを公式台帳・公式価格との重複区間で確認する。基準が分からないものは未確認として保持する。
3. 分割に関係する銘柄では、必要な過去期間を同じ取得時点で取り直して候補系列を作る。違う基準の旧保存値へ、新しい数日分だけを連結しない。
4. 当時値へ戻す場合は、確定した取得基準と公式イベントに基づいて換算する。価格の段差の位置や大きさから係数を推測しない。
5. 同一レスポンス内で矛盾がある、根拠が揃わない、提供元が取得不能な場合は、その候補を正常な系列として公開しない。

同じ取得時点で取り直すことだけで提供元のデータ品質まで保証できるわけではない。無料案の制約として、比較可能な公式情報が不足する直近区間には保留が生じ得る。

## 7. 更新と公開の管理

- 更新処理は銘柄別に未適用の台帳版・未処理の価格観測を持ち、失敗した箇所から再開できるようにする。「イベント登録済み」だけを理由に再計算をスキップしない。
- 台帳の確認状況と、価格への適用状況を分離する。比率確定済みでも価格待ち・再計算待ち・検証失敗・公開済みを区別する。
- 候補の調整済み系列を新しい版として生成し、対象日までの価格と必要なイベントが揃ったことを確認する。その後、公開中の版への参照を一括で切り替える。
- チャート、移動平均、期間騰落率、ランキング等は同じ公開版を使う。修復前の派生データが混ざる場合は当該結果を更新保留とし、正常扱いしない。
- 画面のキャッシュキーに公開版を含める。複数ワーカーのうち一つだけがキャッシュを消して古い値が残る構成を避ける。
- 取得失敗・空の正常応答・未確定・矛盾を区別する。分割予定日に必要な補正が完了していなければ、バッチ成功0件にせず失敗・自動再試行の対象とする。
- 問題のある銘柄は最終確認日を表示し、誤った急落チャートや騰落率を通常表示しない。ほかの銘柄の更新は継続できる構造にする。
- 予定変更・比率訂正・取消では、台帳を改版して当時値から候補を作り直す。「逆向きの係数を掛けて戻す」処理へ依存しない。

公開の可否を判断する入力検証は更新処理が所有し、監査はそれとは別に公開済みの値を独立検査する。

## 8. サーバー側の継続運用

- 毎営業日、JPX予定表と公式開示の追加・訂正を収集。原本の取得成功日・対象期間を記録し、取得停止を検出する。
- 日次バッチは予定台帳更新、価格取得、正規化、調整、関連指標計算、公開の順に処理する。関連する分割開示の収集を価格調整より後に置かない。
- 夜の再試行で未完了銘柄を救済する。再試行条件はLINE等の通知成功とは独立させる。
- 週次・月次には、台帳と公開データの適用版、未解決件数、公式データとの一致を横断検査する。実際のGitHub Actionsの実行定義と処理ログまで用意する。
- Freeでは5回/分を守り、日付指定による全銘柄取得とページングを使う。数千銘柄を高並列で呼び出さない。大きな初期移行は複数回に分割し、進捗をDBへ保存する。
- 公式の訂正も取り込めるよう、直近の重複期間と対象銘柄の過去期間を定期再照合する。処理済み日の追記だけを更新方式にしない。

APIは現行V2仕様のfrom/to・pagination_keyを使う。現行splits.pyのdate_from/date_to指定、ページング未対応、取得失敗時の空配列返却も取得層の見直し対象とする。

## 9. チャート以外の参照

- チャート・テクニカル・期間騰落率は、共通の調整済み価格取得層を使う。各画面のSQLへ個別に補正式を複製しない。
- 当日の実際の終値、約定の再現、保有評価は、当時値とその時点の保有株数を使う。すべての利用箇所を調整後価格へ置き換えることはしない。
- 模擬運用の保有株数は同じ公式イベントを用いて調整する。原本の約定履歴を分割後価格・株数で書き換えない。分割だけで保有資産評価が減らないことを検証する。
- バックテストでは、評価日までに発生したイベントを使う。当時の最低投資金額などを最新の調整価格で判定しない。データ取得日時と実際の情報公開時刻は別であり、分からない公開時刻を取得日時で代用して正確な先読み防止と主張しない。
- 財務の1株当たり指標・株数・価格通知の基準も確認する。公式イベント台帳を共用し、画面ごとに別の分割認定を行わない。

## 10. 移行と完了条件

最初に現在のDBを退避し、取得原本・台帳・新しい価格系列を追加する。キオクシアを含む代表銘柄で新旧を並行比較した後、全銘柄の既存データを出典に沿って移行する。全画面の共通取得層への移行後、影響を受けた派生指標・ランキング・履歴を再計算し、公開版とキャッシュを更新する。無関係な手書きメモ・保有原本等は変更しない。

| 検証ケース | 合格条件 |
|---|---|
| 通常の1:2・1:3分割と併合 | 公式の当時値・係数・調整結果と一致する |
| 今回の分割前日を含む遅延取得 | 取得境界が分割日とずれても同じ基準の系列になる |
| すでに分割調整済みの価格の再取得 | 二重補正を起こさない |
| 同じバッチ・同じイベントの再実行 | 公開値が変わらない |
| 複数回の分割、小さな比率の分割 | 正確な累積係数を使い、値動きで公式イベントを却下しない |
| 訂正・取消、途中失敗からの再開 | 新しい台帳版で再生成し、公開途中の混在が起きない |
| 週足・月足・移動平均・全チャートAPI | 同じ調整済み日足・同じ版を参照する |
| 出来高・ライツイシュー・配当 | 価格と株数の係数、調整対象の違いが保たれる |
| 実際の大幅な値動き | 分割やデータ異常と決めつけて書き換えない |
| 取得障害・予定表停止・矛盾 | 成功0件として隠さず、影響銘柄を保留して自動再試行する |
| 本番での描画と継続更新 | PC/スマホの日足・週足、表示更新日、翌営業日の自動更新を実データで確認する |

最低限の実データ回帰対象は285A、過去の二重補正で問題になった5803・9984、ベンチマーク1306、配当・分配金調整との混同を起こした9282。現在の指標更新停止も別途直し、古い指標を正常な最新結果として使わない。

大きな価格の段差がゼロであることを合格条件にしない。公式データ・イベントとの一致、数式上の整合、再実行の同一性、全参照経路の一致で合否を判定する。

## 11. 採用判断

保存・再生成・共通参照・公開管理の変更はどちらの情報源でも必要。

- **無料方針を維持する基本案:** JPX予定表＋会社公式開示で台帳を作り、既存価格ソースを基準確認付きで取り込む。J-Quants Freeは遅延後の公式照合に利用する。
- **保守負担を減らす追加選択肢:** 本人用の閲覧範囲にそろえたうえで、J-Quants Light（月額1,650円・税込）を日足の主ソースにする。

今回の予防策は「分割を検知できれば終わり」ではなく、適用・検証・公開・翌日の再取得まで完了状態を管理する設計である。
