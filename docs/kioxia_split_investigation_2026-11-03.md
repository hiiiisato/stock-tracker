# キオクシアのウォッチリスト分割補正漏れ調査

調査日: 2026-11-03（JST）
対象: キオクシアホールディングス（285A）、本番ウォッチリストの6か月日足
範囲: 原因調査と再現検証。アプリ・本番DBの修正は未実施。

## 結論

表示経路とデータ更新の両方に不備がある。過去の分割対応は、全画面・日次差分取得・異常監視を通して成立していなかった。

1. 本番 `/api/chart_grid` は調整済み終値を参照せず、OHLCをそのまま返している。
2. DBにも取得時点の異なる価格基準が混在し、285Aの分割記録は0件、過去の `adj_close` は未補正。
3. 分割の採用を「除権日前後のcloseの段差」に依存させているため、取得窓の境界に移動した段差を処理できない。
4. 夜間監視は二重補正を対象とし、今回の「closeとadj_closeが一緒に急変する補正漏れ」を検出しない。
5. コメントに記載されたJ-Quantsへの週次同期が、現行の定期実行設定には存在しない。

単にチャートの参照列を直す、分割係数を追加する、検証の許容幅を広げる、という各対応単独では解消しない。

## 一次情報

会社の[2026年7月31日付の適時開示](https://ssl4.eir-parts.net/doc/285A/tdnet/2859909/00.pdf)に、次の内容が明記されている。

- 普通株式1株を3株へ分割。
- 基準日: 2026-09-30。
- 効力発生日: 2026-10-01。

本番 `disclosures` にも、2026-07-31の同開示のタイトルが保存されている。公式情報自体が存在しなかったわけではない。ただし現行コードは開示本文から分割日・比率を登録せず、Yahooの候補を採用するときの補助判定にだけ利用している。

調査時点のYahoo chart APIは、イベント日2026-09-29、比率3:1の分割を返す。query1とquery2の双方で確認した。これは調査時点の取得結果であり、当日のAPI応答が保存されているわけではない。

## 本番で確認した値

| 日付 | close | adj_close | adj_factor | change_pct |
|---|---:|---:|---:|---:|
| 2026-09-24 | 54,580 | 54,580 | 1 | +0.0183% |
| 2026-09-25 | 55,780 | 55,780 | 1 | +2.1986% |
| 2026-09-28 | 17,780 | 17,780 | 1 | **-68.1248%** |
| 2026-09-29 | 17,880 | 17,880 | 1 | +0.5624% |
| 2026-09-30 | 18,095 | 18,095 | 1 | +1.2025% |

`stock_splits WHERE code = '285A'` は0件。

調査時点のYahooの9月25日closeは18,593.333984375円で、DBの55,780円の約1/3。一方、9月28日以降はYahooとDBが同じ価格基準である。

同じ株数基準に揃えた9月25日→28日の比較は、`17,780 / (55,780 / 3) - 1 = -4.3743%`。保存された-68.1248%は分割による基準差を含む。これは当該2点の比較であり、6か月全体の正しい騰落率を算出したものではない。

## 原因1: ウォッチリストの表示経路が過去の修正対象から漏れている

本番ページをブラウザで開き、6Mが選択された状態のキオクシアの段差を目視確認した。本番APIへのGETでも上表の未補正OHLCが返ることを確認した。

調査開始時のHEADは `19ea6aad26afcbb5ff12b923af97d985f3539340`。
その `app.py` の `api_chart_grid()` は次の列を取得している。

```sql
SELECT dp.code, s.name, dp.date, dp.open, dp.high, dp.low, dp.close
```

`adj_close` を取得せず、そのままJSONへ変換する。チャート上の移動平均もこの価格系列から計算される。

`git blame` ではこのSQLは2026-06-27の `fa9f55c`（チャートグリッド追加）から残存している。2026-06-29の `690ab25` は銘柄詳細チャートのOHLCを `adj_close / close` で調整したが、グリッドのSQLを修正していない。

したがって、DBの `adj_close` だけ直しても、当該本番APIを使うチャートは直らない。

## 原因2: 価格基準の混在を、分割がないことと取り違える

`prices_yahoo._fetch_yahoo()` はYahooのquote.closeを保存し、`adj_close = close`、`adj_factor = 1` とする。取得結果の価格基準・取得時点は行単位で管理していない。

本番ログでは次が確認できる。

- 9月25日: 価格4,205行を保存。
- 9月28日分: 対象営業日の価格未更新を示す通知失敗ログが存在し、当該日の日次価格取得ログは確認できない。
- 9月29日: 価格8,519行を保存。分割処理・整合性監視はいずれも `done / 0`。
- 9月30日以降も分割処理は実行されるが、キオクシアの分割は登録されていない。

この記録と現状の価格系列は、「9月29日の補完取得で28日分も取り込み、その時点ですでに分割後基準となったYahooの過去価格が、25日以前の旧基準データへ接続された」という経緯と整合する。

`splits._verify_split_reflected()` は分割日より前の最後のcloseと、分割日以降の最初のcloseを比較する。今回のイベント日9月29日に対して比較されるのは、すでに同じ基準の17,780円と17,880円である。

```text
実際の比率 = 17,880 / 17,780 ≒ 1.0056
期待比率 = 1/3
実際の比率 / 期待比率 ≒ 3.0169
採用帯 = 0.7～1.4（公式開示が見つかる場合）
判定 = 不採用
```

本番の実数を入力し、現行関数がFalseを返すことを再現した。9月28日を分割前基準へ戻した53,340円（17,780×3）に揃えた比較系列ではTrueを返す。

公式イベントの存在と、その価格行に追加係数が必要かどうかを同じ判定で扱っており、「追加調整を検証できない」が「イベントを保存しない」に直結する設計になっている。

9月29日当日のYahoo応答全文・不採用理由のコンソールログは今回取得していないため、初回不採用時のAPI応答までは断定しない。現在のデータが同じ候補を不採用にし続けること、分割が未登録であること、補正漏れが残ることは実測で確認済み。

## 原因3: 監視と公式への定期同期が防げていない

`run_integrity_check()` の検出条件は次のとおり。

```sql
WHERE rc BETWEEN 0.7 AND 1.4 AND (ra < 0.7 OR ra > 1.4)
```

`rc` はcloseの比率、`ra` はadj_closeの比率。今回はどちらも約0.31875で、closeが通常帯にないため検出されない。これは閾値の微調整ではなく、監視対象が片側だけである問題。

`daily_run.py` のコメントには「週次でJ-Quants公式AdjCに同期」とあるが、現役Pythonコード・GitHub Actions設定を検索した範囲では、週次の定期再構築呼び出しはない。現在の `rebuild()` 呼び出しは新規分割の採用時と整合性異常検出時に限られ、今回のどちらの条件にも入らない。

取得失敗時に空配列を返す経路もあるため、「取得成功・候補なし」と「取得失敗」の状態を分ける必要もある。

## 影響範囲と追加所見

- 登録中5銘柄を対象に、2026-05-01以降の調整済み終値の大幅な日次段差（前日比0.6倍未満または1.7倍超）を調査し、該当したのは今回の285Aの箇所だった。これは監査用の候補抽出であり、価格急変から分割を認定・自動補正する処理ではない。
- 全銘柄に異常がないことを保証する調査は未実施。
- 誤った系列に依存する期間騰落率・移動平均・ランキング等は修復後に依存関係を確認し、再計算対象を特定する必要がある。
- キオクシアの `price_stats.updated_at` は9月25日のまま。9月29日・30日のログには `chg5d` の保存範囲超過による全体計算失敗がある。これは分割漏れとは別の更新停止として扱う必要があり、現時点でキオクシアがその例外を起こしたとは認定しない。

## 推奨する修正の範囲と完了条件

1. **価格データの基準を統一する。** 生値・調整済み値・取得時点の基準を区別し、公式分割イベントの存在を、価格の段差検証の成否と独立して保存する。価格急変だけから新しい分割を推測しない。
2. **全チャートの参照を共通化する。** 銘柄詳細・ウォッチリスト・テーマ・スクリーニングのOHLCを同じ調整済み価格取得層へ集約する。DB修復と表示API修正の双方を行う。
3. **継続更新と監視を完成させる。** サーバー側で公式情報への定期同期を実際に登録する。取得失敗、処理保留、二重補正、補正不足を区別し、未解決を成功0件として隠さない。
4. **実データの一連の検証で完了判定する。** 今回の遅延取得ケースに加え、通常取得、再実行、分割済み価格の再取得、分割比率の異なる事例を確認する。補正を再適用しても値が変わらないこと、分割日と取得境界の両方で連続することを確認する。最後に本番の6か月日足・週足とPC/スマホ表示を確認する。

調査中に並行作業で変更されていたウォッチリストUIの新コードも、保存済み `adj_close` を参照するため、今回のDBの補正漏れ自体は解消しない。UI改善とは別に価格更新経路の修正が必要。
