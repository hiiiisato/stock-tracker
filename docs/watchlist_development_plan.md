# ウォッチリスト改善：本番反映までの開発計画

作成日: 2026-09-20。ステータス: 実装済み。本番DBへ追加専用スキーマを適用済み。

## 目的と初期版の範囲

保存した理由と現在の状況を一覧で確認し、気になる価格への到達を見逃さない。
既存のFlask・TiDB・GitHub Actions・LINEを使い、新しい外部サービスや有料契約は追加しない。

| 機能 | 初期版で実装すること |
|---|---|
| リスト | 自由な作成・名前変更・削除、同一銘柄の複数所属。「すべて」「未分類」からも見られる |
| 保存 | 既存の銘柄名／コード検索を再利用。保存時のリスト指定・メモは省略可能 |
| メモ | 一覧から追加・編集・削除。最新分を表示し、過去分は折りたたむ。銘柄詳細と共通 |
| 一覧 | 終値・価格日・前日比・配当利回り・PER・PBR・3か月ミニチャート・所属リスト・最新メモ |
| 価格通知 | 銘柄ごとに上側／下側を各1つ設定。終値で判定し、翌暦日7:30 JSTにLINEでまとめる |
| 到達表示 | 上限／下限到達・判定日を表示。「確認済み」で消す。通知送信状態とは独立 |

今回は日中監視、条件の自動分類、AIメモ、優待データ取得、売買注文、繰り返し通知、
リストの階層化、ドラッグ並べ替え、指標列の自由編集、通知管理専用ページは追加しない。
「株主優待」は手動で付けるリスト名として扱う。

## 先に固定する動作

- リストを削除しても保存銘柄・メモ・価格通知設定は残す。どのリストにも属さない銘柄は「未分類」へ。
- 「このリストから外す」と「ウォッチリストから削除」を区別する。後者は所属と有効な価格通知を解除し、銘柄メモは残す。
- 同一銘柄のメモ・通知設定はリスト間で共通。既存の `stock_memos` を正として共用する。
  未使用に見える `watchlist.memo` に実データがないか先に確認し、あれば一度だけ既存メモへ保全する。
- リマインダーは終値が「指定価格以上」「指定価格以下」で到達。片側だけでも登録可能。
  0以下・不正値・上下の逆転は保存前に拒否する。
- 新規設定・価格変更・再開は、設定後の最初の市場終了を迎える営業日から有効にする。
  引け後の設定で、その日の過去の終値を遡って通知しない。有効開始日を設定画面に表示する。
- 到達時点でその方向の監視を停止し、イベントとして判定日・判定価格・設定価格を保存する。
  再開は明示操作。上下のもう一方は引き続き有効。
- ウェブの「確認済み」は表示だけを片付ける操作。LINE送信を止めない。
  解除・再設定・ウォッチ削除は、まだ送信処理を開始していない旧設定の通知を取り消す。
- 金曜日の到達は土曜日7:30。休日でも未送信の到達分を処理し、該当ゼロなら送らない。
- 判定日の株価がない銘柄は保留し、古い終値で代用しない。更新遅延は画面に示す。
  未処理日を記録して再実行時に回収し、通知には実際の判定日を載せる。
- 株価更新が7:30に間に合わない場合は通知対象を保持し、次の朝便へ持ち越す。
  更新遅延を補うための高頻度監視は追加しない。
- PERは既存の `stock_fundamentals.per` に合わせて「PER（実績）」と表示する。
  配当利回りは既存の日次計算と同じ根拠を使い、予想／実績の区別を表示する。
  欠損を0と表示せず「—」にする。
- ミニチャートは既存の分割調整済み系列を使い、通知は当日の価格水準と比較する。
  監視中の株式分割・併合は既存の確認済み分割情報に基づき旧価格の設定を要確認として停止する。
  新しい分割推定ロジックや自動的な目標価格変更は作らない。

## 開発の順序

### 1. データ設計と移行準備

既存の `watchlist` と `stock_memos` を維持し、リスト・所属関係・価格設定・到達記録・
通知送信記録の必要なデータだけを追加する。リストと銘柄の組に一意制約を付ける。
通知設定の世代を区別し、過去の到達と再設定後の監視を混ぜない。

移行は追加中心とし、旧アプリでも既存銘柄・メモを読めるようにする。
既存銘柄は「未分類」として扱い、価格通知は利用者が設定するまで発生させない。
再実行可能な明示的な初回移行コマンドを用意する。
本番はGunicorn起動のため、`app.py` の `__main__` にだけ移行を置かない。

完了条件: 既存データを失わない移行・戻し方と、状態の持ち方が確定している。

### 2. 一覧・リスト・メモの実装

PCとスマホで共通の情報設計にする。PCは比較しやすい横並び、スマホは横スクロール不要の縦配置。
銘柄・価格 → 指標／チャート → メモ／価格通知の順に表示し、削除等は補助メニューへまとめる。
既存のダークテーマ・共通ナビ・詳しいチャート表示を維持する。

既存検索とチャート取得を再利用する。ミニチャートは必要な銘柄分をまとめて取得し、
取得上限を超える銘柄数でもページ単位等に分けて表示できるようにする。
メモや所属を保存しても選択中リスト・スクロール位置を保つ。
保存に失敗した入力は消さず、再試行できる。状態はDOMではなくJSオブジェクトで管理する。

既存の銘柄詳細の保存ボタンからもリスト・任意メモを指定できるようにする。
SQLのプレースホルダー、メモ／リスト名のHTMLエスケープ、入力検証を実装時に揃える。

完了条件: 実データで、分類→メモ追加→再表示の一連操作がPCとスマホで成立する。

### 3. 到達判定と朝のLINE通知

日次の価格・分割処理後に軽量な到達判定を入れ、AI処理やレポート生成の成功に依存させない。
再実行時に未処理分を回収し、日次バッチの完了ガードで判定が永久に飛ばされないようにする。
画面表示は保存済みの到達記録を読む。ページ閲覧を通知発生のきっかけにはしない。

毎朝7:30 JSTの専用GitHub Actionsを追加する。届くべき時刻を過ぎた未送信分を対象にし、
実行が遅れても対象営業日を取り違えない。既存の失敗時再実行の対象にも加える。
実行の重複を抑え、送信前に本文と再送キーをDBへ確定してから既存の `line_notify.py` で送る。
LINEの送信上限に収まらない場合も黙って本文を切らず、件数と一覧リンクで全対象を辿れる形にする。

同じ送信の再試行は同じ `X-Line-Retry-Key` と本文を使う。API受付後にDB保存だけが失敗した場合も、
再送による重複を防ぐ。再送キーの有効期間は24時間なので、受付が不明なまま期間を過ぎた送信は
自動で新規送信し直さず、確認が必要な失敗として残す。既存の日次レポート送信との互換性を保つ。
朝便を止められる最小の送信有効設定を用意し、本番反映の最後に有効化する。

完了条件: 終値判定・ウェブ表示・翌朝送信がつながり、再実行と失敗からの復旧で重複しない。

### 4. 必要最小限の検査

新しいテスト基盤は導入せず、既存のPythonテストとブラウザー確認を使う。
以下を合格条件にし、問題が出た範囲だけ追加検査する。

| 重点 | 最小の検査 |
|---|---|
| データ保全 | 少数の既存データのコピーで移行を2回実行。複数リスト所属、一方のリスト削除後も銘柄・メモが残ることを確認 |
| 判定の正確さ | 上下の一致／超過／未到達、設定後の有効日、価格欠損・分割時の保留を小さなテーブル形式の自動テストで確認 |
| 日時・二重送信 | 金曜→土曜7:30、7:30前は送らない、遅延起動、再実行、LINE受付後のDB失敗・再送期限超過を固定時刻と擬似応答で確認 |
| 主要操作・表示 | PC幅とスマホ幅で各1周。検索保存→複数分類→メモ→通知設定→フラグ確認。再読み込み／戻る、空一覧、保存失敗、HTML記号を含む入力も同じ確認に含める |
| 数値・既存への影響 | 実DBの数銘柄で終値・PER・利回り・チャートを照合。欠損銘柄を含める。触ったLINE・日次ガードの既存テストと構文検査を実行 |

検証用の書き込みは隔離したDBまたは検証データで行い、本番銘柄を勝手に編集しない。
全ページの総点検、ブラウザー総当たり、負荷試験、大量のスクリーンショット試験、
実装をそのままなぞる細かなテスト追加は行わない。

### 5. 本番反映と初回確認

1. 変更を `codex/` ブランチにまとめる。作業中の別機能の変更を混ぜない。
   Renderの実際の配信対象ブランチ・自動デプロイ設定を確認する（リポジトリだけでは未確認）。
2. 対象の個人データを必要範囲だけ退避し、追加マイグレーションを実行する。
   退避ファイルはリポジトリに含めない。
3. 価格通知の送信を無効にした状態で本番コードを反映する。Renderの起動・`/health`・
   ウォッチリストの実表示を確認し、既存の登録件数とメモを照合する。
4. 既存のLINE認証情報を再利用し、朝便の設定と送信対象をドライランで確認する。
   利用者への実送信テストは本番反映作業で明示的に了承された1通に限定する。
5. 朝便を有効化する。翌朝の初回実行結果を確認し、到達分があれば通知と送信記録を照合する。
   対象ゼロの場合は「送信0件で正常終了」を確認し、自然な到達を待つためだけにリリースを止めない。
6. `ARCHITECTURE.md` と移行・通知停止／再実行の短い手順を更新して完了とする。

切り戻しは「朝便の送信停止 → 直前のWeb／バッチ版へ戻す」の順に行う。
追加テーブルと新規メモは削除せず、復旧後に再利用できる状態を保つ。
アプリを戻すだけでGitHub Actionsの送信まで止まるとは考えない。

## 実装の配置目安

- `app.py`：既存ルート・銘柄詳細との接続。ウォッチリスト固有の処理は小さな専用モジュールとUIファイルへ分ける。
- データ操作用モジュール：リスト・所属・共通メモ・価格設定。汎用管理フレームワークにはしない。
- 価格通知用モジュール：判定・到達記録・送信。日次と朝便から同じ処理を呼ぶ。
- `daily_run.py`：到達判定への接続。`line_notify.py`：既存互換の再送キー対応。
- `.github/workflows/`：朝便と既存失敗時再試行への登録。
- `tests/`：判定・通知の重要なケースに限定した追加。既存テストを活用する。

## 外部仕様の根拠

- GitHub Actionsは指定時刻に遅延することがあるため、7:30は予約時刻であり到着時刻の保証ではない。
  [GitHub公式：schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)
- LINEの再試行は同じ本文・宛先・再送キーを使用する。キーは初回要求から24時間有効。
  API受付成功は端末への到着確認ではない。
  [LINE公式：Retry failed API requests](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)
